## Tick budgeting and amortization (round-robin, time-sliced queues, staggering by entity id, avoiding periodic spikes)

### Takeaway
Vanilla 1.21.1 already staggers mob AI by entity id and throttles path recomputation; server forks (Spigot/Paper entity activation range, Pufferfish DAB) and ServerCore (which has NeoForge 1.21.1 builds) add distance-based tick skipping. A content mod with a big simulation should copy these patterns for its own work: stagger by `(gameTime + id) % N`, drain job queues against a per-tick nanosecond budget, and never run "everyone at once" on day rollover or on autosave.

### Cited Findings
- **Vanilla stagger by entity id:** `Mob.serverAiStep()` computes `i = tickCount + getId()`; when `i % 2 != 0` it only calls `targetSelector.tickRunningGoals(false)` / `goalSelector.tickRunningGoals(false)`, otherwise it runs the full `targetSelector.tick()` / `goalSelector.tick()` (goal re-selection). Sensing and `navigation.tick()` run every tick. So goal selection already runs every other tick, and the id offset spreads the mobs over two buckets. — [MC/Neo 21.1.265 src: Mob#serverAiStep](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Vanilla goal delays are halved unless a goal opts out:** `Goal.adjustedTickDelay(n)` returns `n` if `requiresUpdateEveryTick()` is true, else `reducedTickDelay(n) = Mth.positiveCeilDiv(n, 2)`. `requiresUpdateEveryTick()` defaults to `false`. Custom goals should express cooldowns through `adjustedTickDelay` so they stay right under the every-other-tick scheme. — [MC/Neo 21.1.265 src: Goal](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Vanilla throttles path recomputation:** `PathNavigation.recomputePath()` only recomputes if `level.getGameTime() - timeLastRecompute > 20`, otherwise it sets `hasDelayedRecomputation = true`, which is checked in `tick()` and `shouldRecomputePath()`. — [MC/Neo 21.1.265 src: PathNavigation](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Spigot/Paper entity activation range (EAR):** entities beyond a per-category range from any player tick less often. Defaults: animals 32, monsters 32, raiders 64, misc 16, water 16, villagers 32, flying-monsters 32 blocks; 0 or less disables it per category. `wake-up-inactive` wakes out-of-range entities periodically: animals every 1200 ticks for 100 ticks (max 4 per tick), flying-monsters 200/100/8, monsters 400/100/8, villagers 600/100/4; the "every" values are minimums because the per-tick caps can delay waking. Villager options: `villagers-work-immunity-after` 100, `villagers-work-immunity-for` 20, `villagers-active-for-panic` true, `tick-inactive-villagers` true. Paper's `max-tick-time` (tile/entity 50 ms) does not operate. — [PaperMC docs: spigot.yml reference](https://docs.papermc.io/paper/reference/spigot-configuration/)
- **Pufferfish Dynamic Activation of Brain (DAB):** brain tick frequency is `freq = distanceToPlayer² / 2^activation-dist-mod`; with the default modifier 8 the divisor is 256, so an entity 16 blocks away ticks about every tick and one 32 blocks away about every 4 ticks. `start-distance` exempts nearby entities; `max-tick-freq` caps the interval (example value 20 = at least once per second); the docs advise never lowering the modifier below 6. DAB only affects Brain-based mobs (villagers, axolotls, hoglins, zombified piglins, goats). `inactive-goal-selector-disable` stops inactive entities selecting new goals ("may break some farms"). — [Pufferfish docs](https://docs.pufferfish.host/setup/pufferfish-fork-configuration/); sample config values (start-distance 12, max-tick-freq 20, activation-dist-mod 8) in a [mirrored pufferfish.yml](https://huggingface.co/spaces/OrbitMC/Server/blob/main/pufferfish.yml)
- **ServerCore (Fabric + NeoForge):** ports Spigot/Paper EAR "with some optional extras"; "dynamic performance checks" automatically adjust chunk-tick distance, view distance, simulation distance and mobcaps from measured tick time; "villager lobotomization" makes villagers stuck in 1x1 spaces tick less; features that change vanilla behaviour are off by default. Parts are ported from Paper, Purpur and Airplane patches (GPL-3.0). — [ServerCore GitHub](https://github.com/Wesley1808/ServerCore). NeoForge 1.21.1 builds exist up to `1.5.19+1.21.1` (2026-06-24). — [Modrinth API: ServerCore versions](https://api.modrinth.com/v2/project/servercore/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **Activity-based throttling for physics objects:** Sable Optimizer marks a Sable sub-level inactive when its velocity stays below `velocityThreshold` (0.01) for `inactivityThresholdTicks` (400 balanced), then updates it less often (heatmap every 10 ticks instead of 4, pose/force every 5 substeps, actors every 4 ticks in the balanced preset). — [Sable Optimizer on CurseForge](https://www.curseforge.com/minecraft/mc-mods/aeronautics-sable-optimizer)
- **Periodic-save spikes are a known 1.21.x problem:** a Mojira report against 1.21.4 describes a roughly 3-second single-tick spike every 5 minutes traced to save methods (later about 500 ms); unresolved. — [MC-279194 (Mojira)](https://bugs-legacy.mojang.com/browse/MC-279194), [mojira.dev mirror](https://mojira.dev/MC-279194)

### Inferences
- The same per-id staggering is the cheapest pattern for the mod's own per-unit or per-hold work: run expensive checks only when `(gameTime + id) % N == 0`, with N chosen per job (e.g. 20 for target search, 100 for morale/supply). This is exactly vanilla's `Mob#serverAiStep` idea generalized.
- "Daily nation decisions", marriages, succession checks, sea-lane updates and similar should not all fire on the tick the day changes. Either spread entities over the whole day (`hash(holdId) % ticksPerDay` as each hold's decision tick) or put them in a queue drained in `ServerTickEvent.Post` until a `System.nanoTime()` budget (for example 1–3 ms) is spent, and carry the rest to the next tick. The round-robin cursor must survive saves (store it in SavedData) or be derived from game time.
- A distance-tiered tick for the mod's own NPCs and ships (DAB-like: interval grows with squared distance to nearest player, capped) matches what Paper/Pufferfish/ServerCore do and needs no mixins if the mod owns the tick loop.
- Because Recruits are goal-based (not Brain-based, inferred from the jar's `AsyncPathNavigation`/goal classes), Pufferfish-style DAB would not affect them; ServerCore's EAR is the server-side tool that would apply to them, and its "immunity" rules need checking so soldiers in a battle near a player are never throttled.

### Gaps
- No published source found for the internal job schedulers of Minecolonies, Create, Millénaire or Valkyrien Skies (searches returned only indirect material). Per-tick millisecond budgets used by those mods are undocumented in what I could reach.
- No measured gains (MSPT before/after) for EAR/DAB on modded NeoForge servers were found; Pufferfish docs give the formula, not numbers.
- ServerCore's exact EAR immunity rules and default ranges were not on the README; they live in its `docs/config` examples, which I did not fetch.

## Off-thread work in 1.21.1 (what is safe, how to hand results back, pool sizing, C2ME/Moonrise)

### Takeaway
Only pure computation over immutable snapshots is safe off-thread; any `Level`/chunk access from a worker either blocks on the main thread or corrupts state. Do the planning (city layout, road graphs, battle resolution, simulation decisions) on a small dedicated executor, then apply results on the server thread in budgeted slices. C2ME (alpha, actively maintained for NeoForge 1.21.1) and Moonrise (NeoForge 1.21.1 betas, now unsupported) are mutually incompatible and both police thread misuse.

### Cited Findings
- **Chunk access from a worker thread blocks:** `ServerChunkCache.getChunk(x, z, status, requireChunk)` checks `Thread.currentThread() != this.mainThread` and, if so, does `CompletableFuture.supplyAsync(() -> getChunk(...), mainThreadProcessor).join()`. A worker calling it is parked until the main thread runs the request; on the main thread a missing chunk is waited for with `mainThreadProcessor.managedBlock(future::isDone)`, i.e. a synchronous load/generate stall. `getChunkNow(x, z)` exists as the non-loading variant. — [MC/Neo 21.1.265 src: ServerChunkCache](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Vanilla thread pools:** `Util.BACKGROUND_EXECUTOR` ("Worker-Main-N", used by worldgen and other background work) is sized `Mth.clamp(availableProcessors - 1, 1, max.bg.threads)`, where the `max.bg.threads` system property is limited to 1–255; `Util.IO_POOL` threads are named "IO-Worker-". — [MC/Neo 21.1.265 src: Util](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **NeoForge network handlers:** payload handlers run on the main thread by default; `registrar.executesOn(HandlerThread.NETWORK)` moves later registrations to the network thread; from a network-thread handler, `context.enqueueWork(...)` returns a `CompletableFuture` and exceptions are silently swallowed unless `.exceptionally(...)` is chained. — [NeoForge docs 1.21.1: Registering Payloads](https://docs.neoforged.net/docs/1.21.1/networking/payload)
- **C2ME:** parallelizes chunk generation, I/O and loading; ships thread sanitizers such as `CheckedThreadLocalRandom` for world random, part of "UWRAD" (unsafe world random access detection), "to prevent mods from screwing up Minecraft internals"; false positives are said to be rare and detections should be reported to the mod author; mod world generators "may cause compatibility issues due to certain design assumption used by mod authors being broken". — [C2ME GitHub](https://github.com/RelativityMC/C2ME-fabric); [C2ME NeoForge listing](https://minecraftbible.com/mods/c2me-neoforge)
- **C2ME NeoForge 1.21.1 status:** 73 alpha builds, newest `0.4.0-alpha.0.124+1.21.1` (2026-10-27). Changelog items: "fully threaded scheduling" (0.3.0.68), "strict detection for scheduled tick access" (0.3.0.40), "prevent item drops on worldgen threads" (0.3.0.93), "bandaid for create aeronautics" (0.4.0.112), "fix: ServerCore broadcast optimization compat" (0.3.0.58), plus several race-condition and future-synchronization fixes. — [Modrinth API: C2ME NeoForge 1.21.1 versions](https://api.modrinth.com/v2/project/c2me-neoforge/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **Moonrise:** official port of Paper's chunk system rewrite and Starlight to Fabric/NeoForge; optimizes entity movement/collision/tracking, chunk tick/load/gen/save, and "block/entity retrieval used by pathfinding and entity AI"; auto-disables conflicting parts of Lithium and FerriteCore; **incompatible with C2ME** (C2ME modifies the chunk system Moonrise replaces wholesale) and with ScalableLux. Only 26.x versions are now supported. — [Moonrise GitHub](https://github.com/Tuinity/Moonrise). NeoForge 1.21/1.21.1 builds exist up to `0.1.0-beta.15+2eae1b1` (2025-10-10). — [Modrinth API: Moonrise versions](https://api.modrinth.com/v2/project/moonrise-opt/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **Off-thread pathfinding in practice:**
  - Villager Recruits 1.15.2 (NeoForge) runs pathfinding on a `ThreadPoolExecutor` (`AsyncPathProcessor.pathFindingExecutor`, plus `NodeEvaluatorCache`/`NodeEvaluatorGenerator` classes). — [Recruits jar](file:///C:/Users/carat/.gradle/caches/modules-2/files-2.1/maven.modrinth/villager-recruits/IYZdzeH9/950b96c29619523c517133f01bc4a7347e9c050b/villager-recruits-IYZdzeH9.jar)
  - Its config sets `UseAsyncPathfinding = true` (default true), described as improving "TPS on huge numbers of recruits ... a lot" but "useless if machine has only one physical core", with "small delays in path finding". `AsyncPathfindingThreadsCount = 1` (default 1, range 1–16, "Usually good value is n/4, where n is amount of logical cores"). — [recruits-server.toml](file:///C:/Users/carat/curseforge/minecraft/Instances/RafasConquest1.21Neo/config/recruits-server.toml)
  - The Minecolonies-derived PerViamInvenire pathfinder builds a cache of the chunks between source and targets, then runs an adapted A* "on a thread pool". — [PerViamInvenire GitHub](https://github.com/ldtteam/PerViamInvenire)
  - Pufferfish+ offers `enable-async-entity-pathfinding` and `enable-async-entity-tracker`; the async tracker still sends packets on the main thread and they may arrive out of order. — [Pufferfish docs](https://docs.pufferfish.host/setup/pufferfish-fork-configuration/)
- **Snapshot-then-write pattern in Paper's SavedData IO:** the main thread serializes to `CompoundTag` and clears the dirty flag; a single-thread daemon executor per `DimensionDataStorage` does `NbtIo.writeCompressed`; shutdown/close joins all writes synchronously. — [Paper patch "Write SavedData IO async"](https://ayakael.net/mirrors/papermc/src/commit/ca07564e47a84a1b934b4e14e5645c6c23d817d6/patches/server/Write-SavedData-IO-async.patch)

### Inferences
- **Safe off-thread:** pure functions of seed/noise and of data copied out of SavedData (city/capital layout planning, road A* over a precomputed height grid, harbour-cut planning, statistical battle resolution, nation decision scoring, sea-lane time simulation). Inputs must be copied on the server thread (or be immutable records); outputs are plain data (block lists, decisions).
- **Never off-thread:** `Level#getBlockState`/`setBlock`, `getChunk` (blocks on main thread, see above), entity creation/movement/removal, `Level.random` (C2ME's UWRAD flags it; use a per-task `RandomSource.create(seed)`), mutating SavedData objects that the main thread also reads, and sending packets that depend on live entity state.
- **Hand-back:** apply results via `server.execute(...)` (MinecraftServer is a `ReentrantBlockableEventLoop`) or, better for large results, push them into a concurrent queue that the mod drains in `ServerTickEvent.Post` under a per-tick budget, so a big result does not land as one long task. Check a generation/epoch counter before applying, so stale results (hold changed owner, battle ended) are dropped.
- **Pool sizing:** use one small named daemon pool owned by the mod (1–2 threads; Recruits' own default is 1) rather than `ForkJoinPool.commonPool()` or `Util.backgroundExecutor()`, which worldgen (and C2ME, DH) already saturate. Shut it down on `ServerStoppingEvent`.
- Since the mod sets up worldgen and Sable ships, it should be tested with C2ME (the actively maintained 1.21.1 option) rather than Moonrise (unsupported on 1.21.1 now); C2ME's Create Aeronautics band-aid hints that Sable-based content has hit its thread checks before.

### Gaps
- No NeoForge-official document listing which vanilla APIs are thread-safe was found.
- C2ME's full list of sanitizers ("a few others" besides CheckedThreadLocalRandom) is not documented on the pages reached.
- Default of Recruits' `UseAsyncTargetFinding` (the string exists in `RecruitsServerConfig.class`) could not be read; it does not appear in the generated toml.

## Large NPC counts (goals, pathfinding, target selection, collisions, LOD/abstract battles, Villager Recruits specifics)

### Takeaway
Per-unit costs that scale badly are pathfinding (node budget = FOLLOW_RANGE × 16), entity AABB queries (target search, pushing every tick) and goal re-selection. Recruits already offloads pathfinding to a thread pool (1 thread by default). For hundreds of soldiers the mod should cut the number of real queries (formation-level paths, one spatial grid per battle, fewer real entities via LOD/abstract resolution) rather than rely on generic optimizers.

### Cited Findings
- **Pathfinding node budget:** the `PathNavigation` constructor sizes the path finder from `Mth.floor(mob.getAttributeValue(Attributes.FOLLOW_RANGE) * 16.0)`; `setMaxVisitedNodesMultiplier(float)` scales it; `createPath(...)` passes `FOLLOW_RANGE` as the search radius to `pathFinder.findPath(region, mob, targets, followRange, accuracy, maxVisitedNodesMultiplier)` over a `PathNavigationRegion` snapshot. A large FOLLOW_RANGE makes every failed path search expensive. — [MC/Neo 21.1.265 src: PathNavigation](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Pushing/cramming cost:** every server tick `LivingEntity.pushEntities()` calls `level.getEntities(this, getBoundingBox(), EntitySelector.pushableBy(this))`; if the list exceeds the `maxEntityCramming` game rule, a 1-in-4 roll counts non-passengers and deals 6 cramming damage; then `doPush` runs for each neighbour. Densely packed formations pay O(neighbours) per unit per tick. — [MC/Neo 21.1.265 src: LivingEntity#pushEntities](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Entity queries walk entity sections:** `EntitySectionStorage.getEntities(AABB, consumer)` iterates every accessible non-empty section overlapping the box (`forEachAccessibleNonEmptySection`) and filters entities inside. Cost grows with box size and entity density. — [MC/Neo 21.1.265 src: EntitySectionStorage](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Lithium (has NeoForge 1.21.1 builds) targets exactly these costs:** `mixin.ai.pathing` (faster block-to-node lookup and chunk cache during path evaluation), `mixin.ai.task.launch` / `memory_changes` / `ai.sensor` (brain), `mixin.entity.collisions.unpushable_cramming` (separate pushable-entity list for cramming tests), `entity.collisions.intersection` and `.movement` (faster block/entity access), `collections.entity_by_type`, `alloc.entity_iteration`. — [Lithium NeoForge mixin config](https://raw.githubusercontent.com/CaffeineMC/lithium/develop/lithium-neoforge-mixin-config.md). NeoForge 1.21.1 builds: `mc1.21.1-0.14.0-beta.1` (2024-10-16) through `mc1.21.1-0.15.4-neoforge` (2026-06-27). — [Modrinth API: Lithium NeoForge 1.21.1](https://api.modrinth.com/v2/project/lithium/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **Paper avoids chunk loads during pathfinding:** Aikar's patch makes `WalkNodeEvaluator.getPathTypeFromState` use `world.getBlockStateIfLoaded(pos)` and return `PathType.BLOCKED` when the chunk is not loaded. — [Paper patch "Do not load chunks for Pathfinding"](https://ayakael.net/mirrors/papermc/src/commit/38e1465620f2a0e0baf2b6156df72f653be80781/patches/server/Do-not-load-chunks-for-Pathfinding.patch)
- **Villager Recruits specifics (1.15.2 NeoForge, the version the project builds against):** async pathfinding classes (`AsyncPathNavigation`, `AsyncGroundPathNavigation`, `AsyncWaterBoundPathNavigation`, `AsyncPathProcessor`, `NodeEvaluatorCache`), an `entities/ai/async/AsyncManager`, its own `RecruitPathNavigation`/`RecruitsPathNodeEvaluator`, `FormationUtils` and `PathAnalyzer`. — [Recruits jar](file:///C:/Users/carat/.gradle/caches/modules-2/files-2.1/maven.modrinth/villager-recruits/IYZdzeH9/950b96c29619523c517133f01bc4a7347e9c050b/villager-recruits-IYZdzeH9.jar). - **Public Recruits performance reports are thin:** GitHub issue searches for "lag" and "performance" in talhanation/recruits returned 0 results. — [issues?q=lag](https://github.com/talhanation/recruits/issues?q=is%3Aissue+lag), [issues?q=performance](https://github.com/talhanation/recruits/issues?q=is%3Aissue+performance). A user review calls the mod "pretty optimized" but says it "could cause some lag when there are too many recruits". — [MODDEX review](https://moddex.gg/mod/recruits/reviews/3767)

### Inferences
- **Raise Recruits' pathfinding pool:** the default of 1 thread is low for 300+ unit battles; the config's own guidance (n/4 logical cores) is the first, zero-code change. Remember the user's PC-memory note: more threads are cheap in memory, but test on the target machine.
- **Formation-level pathfinding:** compute one path per formation/wing (banner or leader) and give each soldier a slot offset (`FormationUtils` already exists in Recruits) with short straight `moveTo` legs; individual A* only for the last few blocks or when blocked. This turns N path searches into roughly one per wing.
- **Low FOLLOW_RANGE + `setMaxVisitedNodesMultiplier(<1)`** on soldiers the mod spawns caps the worst-case search; failed searches (target across a river or wall) are the expensive case.
- **One spatial grid per battle:** each tick (or every 5–10 ticks) bucket all battle units into a `Long2ObjectOpenHashMap` keyed by packed cell (8–16 blocks); target selection and "nearest enemy" read the grid instead of `getEntitiesOfClass(AABB)` per unit. Retarget on a staggered schedule (`(gameTime + id) % 10`).
- **Pushing:** inside a tight formation the vanilla push loop runs every tick for every soldier. If the mod controls the soldier class or can set `maxEntityCramming` for the battle area, avoid cramming damage at 24+ overlapping units (default rule). Lithium's `unpushable_cramming` helps only the cramming count, not `doPush`.
- **LOD tiers for battles:** (1) no player within N chunks: resolve by numbers on hold/army data (no entities); (2) player watching from afar (battle camera/DH sprites): only a representative subset of real entities, the rest as data; (3) player in the fight: full entities. This is the RTS/Total-War style LOD that the project's naval design already uses ("real → LOD → sprite"). Which units become data must be agreed with the user (memory: ask before repurposing units).

### Gaps
- No published measurements of Recruits TPS cost per unit, and no Recruits issue threads about large armies were found.
- Minecolonies' current pathfinding thread settings and Millénaire's approach were not documented in reachable sources.
- Exact effect of ServerCore EAR on Recruits soldiers (whether they count as "monsters", "villagers" or "misc") is unknown.

## Bulk block placement in worldgen and at runtime (setBlock flags, section writes, lighting, heightmaps, chunk loads, tickets, WorldEdit/FAWE, Chunky)

### Takeaway
Every `LevelChunk.setBlockState` updates four heightmaps and may queue light work regardless of flags; flags only remove neighbour, shape and client-sync work. The fastest safe path is to place cities as worldgen structures (the chunk is generated with them, lit once, no tickets, compatible with Chunky/DH/C2ME). For runtime placement, only touch loaded chunks, use minimal flags in budgeted slices, and never call `getChunk` on unloaded chunks from a tick (synchronous load/gen stall).

### Cited Findings
- **Flag constants (Mojang names, 1.21.1):** `UPDATE_NEIGHBORS = 1`, `UPDATE_CLIENTS = 2`, `UPDATE_INVISIBLE = 4`, `UPDATE_IMMEDIATE = 8`, `UPDATE_KNOWN_SHAPE = 16`, `UPDATE_SUPPRESS_DROPS = 32`, `UPDATE_MOVE_BY_PISTON = 64`, `UPDATE_NONE = 4`, `UPDATE_ALL = 3`, `UPDATE_ALL_IMMEDIATE = 11`, `UPDATE_LIMIT = 512`. There is no "skip lighting" flag in 1.21.1. — [MC/Neo 21.1.265 src: Block](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar). Yarn javadoc for the same values: 1 "Sends a neighbor update event to surrounding blocks"; 2 "Notifies listeners and clients who need to react when the block changes"; 4 suppresses the client render pass; 8 "Forces a synchronous redraw on clients"; 16 "Bypass virtual block state changes and forces the passed state to be stored as-is" (i.e. no neighbour shape updates); 32 "Prevents the previous block (container) from dropping items when destroyed"; 64 piston move. — [Yarn 1.21.1 Block javadoc](https://maven.fabricmc.net/docs/yarn-1.21.1+build.3/net/minecraft/block/Block.html), [Yarn constant values](https://maven.fabricmc.net/docs/yarn-1.21.1+build.3/constant-values.html)
- **Work done by every chunk-level set:** `LevelChunk.setBlockState(BlockPos, state, isMoving)` updates the `MOTION_BLOCKING`, `MOTION_BLOCKING_NO_LEAVES`, `OCEAN_FLOOR` and `WORLD_SURFACE` heightmaps; calls `lightEngine.updateSectionStatus(pos, ...)` when a section becomes empty/non-empty and `lightEngine.checkBlock(pos)` when `LightEngine.hasDifferentLightProperties(...)`; runs `oldState.onRemove(...)` and (unless `captureBlockSnapshots`) `state.onPlace(...)` server-side. — [MC/Neo 21.1.265 src: LevelChunk](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)

### Inferences
- **Recommended runtime flag set for interior bulk placement:** `UPDATE_CLIENTS | UPDATE_KNOWN_SHAPE` (18), plus `UPDATE_SUPPRESS_DROPS` (50) when replacing containers. Skip `UPDATE_NEIGHBORS` so water, sand, rails and redstone do not cascade; do a final `UPDATE_ALL` pass only on the outer boundary (or on blocks whose shape depends on neighbours: fences, walls, panes, stairs) so connections look right.
- **Section-write path (FAWE style) for very large runtime edits:** for each loaded chunk, write `LevelChunkSection.setBlockState(..., false)` directly, then (a) recompute heightmaps (`Heightmap.primeHeightmaps`), (b) relight the touched sections through the light engine, (c) mark the chunk unsaved, (d) resend the chunk to tracking players (`ClientboundLevelChunkWithLightPacket`), (e) handle block entities separately. This avoids per-block light/heightmap work but bypasses `onPlace`/`onRemove`, so it suits terrain/stone/planks, not functional blocks. Light behaviour differs under Starlight/ScalableLux/Moonrise, so test with those.
- **Prefer worldgen structures for cities, roads and farms where possible:** a `Structure` + `StructurePiece` places blocks into a `WorldGenRegion` during the features step, before lighting and before the chunk is ever sent, with no tickets and no sync loads. It is also what DH's `INTERNAL_SERVER` and Chunky pregen naturally include. Post-load placement (the current approach for whole cities) forces either a ticketed load of every chunk or deferral.
- **Deferral queue for unloaded chunks:** store pending edits keyed by `ChunkPos.toLong()` in SavedData; apply them in a budgeted tick drain when `getChunkNow` returns non-null (e.g. after a `ChunkEvent.Load`, but apply on the next tick rather than inside the event). This replaces forced loads.
- **Budget:** cap blocks per tick by a `nanoTime` budget rather than a count, because cost per block varies (light changes, block entities). A city placed over 100–200 ticks is invisible to players; a 2-second single-tick placement is a visible freeze.

## Distant Horizons: server-side/distant generation cost and how a structure mod should cooperate

### Takeaway
DH generates LODs by asking for chunks through one of four modes; only `INTERNAL_SERVER` runs real server generation (so it includes mod structures, at the cost of server lag and region-file storage). Content placed after chunk load is not in DH's LODs until DH re-reads the chunk; the API's `overwriteChunkDataAsync` lets a mod push fresh LOD data for loaded levels. DH 2.3+ supports dedicated servers and server-side LOD generation.

### Cited Findings
- **Generator modes (fastest to slowest):** `PRE_EXISTING_ONLY` (no new terrain, LODs only from existing chunks), `SURFACE` (surface only, no caves/trees/structures), `FEATURES` (also structures; "may cause world generation bugs or instability"), `INTERNAL_SERVER` (server generates or loads each chunk; most compatible, "places structures correctly", "may cause server/simulation lag", saves chunks to Minecraft region files). — [DH API: EDhApiDistantGeneratorMode](https://distant-horizons-90c399.gitlab.io/com/seibel/distanthorizons/api/enums/worldGeneration/EDhApiDistantGeneratorMode.html)
- **World generator override API:** `IDhApiWorldGenerator` has `generateChunks(...)` (return type `VANILLA_CHUNKS`, default) receiving `EDhApiDistantGeneratorMode` and an `ExecutorService worldGeneratorThreadPool`; `generateApiChunks(...)` (API 2.0, `DhApiChunk`, must include air and lighting or LODs render black); `generateLod(...)` (API 4.0, fills a pooled `IDhApiFullDataSource` that must not be referenced outside the call); `runApiValidation()` (enable in dev, disable in release); `preGeneratorTaskStart()`. — [DH API: IDhApiWorldGenerator](https://distant-horizons-90c399.gitlab.io/com/seibel/distanthorizons/api/interfaces/override/worldGenerator/IDhApiWorldGenerator.html)
- **Pushing updated LODs:** `IDhApiTerrainDataRepo.overwriteChunkDataAsync(levelWrapper, Object[] chunkObjectArray)` sets the LOD for a chunk; works only for a loaded level; the update is queued behind other chunks; it is replaced when a player goes near or the chunk changes; the array must match what `generateChunks` expects (otherwise `ClassCastException`). The repo also offers read APIs (`getColumnDataAtBlockPos`, `getAllTerrainDataAtChunkPos`, `raycast`) and a `SoftReference` cache. — [DH API: IDhApiTerrainDataRepo](https://distant-horizons-90c399.gitlab.io/com/seibel/distanthorizons/api/interfaces/data/IDhApiTerrainDataRepo.html)
- **Server support:** DH 2.3.0 lists client, server and both environments, with "Server LOD generation" in the changelog. — [DH 2.3.0 for 1.21.1 on Modrinth](https://modrinth.com/mod/distanthorizons/version/2.3.0-b-1.21.1)
- **Community reports:** a GitLab issue reports the Internal Server mode creating LOD chunks "too early", with only pre-existing-only avoiding it. — [DH issue #1060](https://gitlab.com/distant-horizons-team/distant-horizons/-/issues/1060). A support answer says server-side generation can only be limited by config, not fully stopped. — [Answer Overflow thread](https://www.answeroverflow.com/m/1402948133293396001). Another admin saw DH detect disparities between a Chunky-pregenerated LOD database and the world after structures were built. — [Answer Overflow thread](https://www.answeroverflow.com/m/1276755245191532637)
- **Override example:** Chunksmith registers as DH's world-generator override so DH shows pregenerated areas without generating itself. — [Chunksmith on Modrinth](https://modrinth.com/project/chunksmith)

### Inferences
- Cities placed after chunk load will be missing from LODs generated by `SURFACE`/`FEATURES`, and from `INTERNAL_SERVER` LODs built before the city was placed. After placing a city in loaded chunks, the mod can call `overwriteChunkDataAsync` for the touched chunks (on the server side or wherever DH's level wrapper is loaded) so distant views update; otherwise DH will refresh when it next sees the chunk change.
- `INTERNAL_SERVER` mode makes DH a heavy consumer of server generation threads and of chunk loads; with the mod also placing cities and roads, DH generation should be pregenerated off-hours or throttled through DH's own config on the server.
- If cities became worldgen structures (previous section), DH `INTERNAL_SERVER` and Chunky pregen would include them automatically, with no API calls.

### Gaps
- DH's server-side config option names, generation thread count defaults and rate limits were not found in reachable docs.
- Whether DH's `FEATURES` mode runs modded `Structure`s (vs vanilla features only) is not stated.
- The exact DH API version shipped in the project's DH jar (`distant_horizons_version=9w34y8ai`) was not checked.

## Physics sub-levels (Sable / Valkyrien Skies-style ships): costs, limits, keeping many ships cheap

### Takeaway
Sable is a heavy, mixin-intrusive Rapier-based (Rust) physics library with no published limits; the community answer to its cost is activity detection (sleeping ships update less) and server-side budgets. The mod's existing design (far ships simulated by time, Sable only near players) is the main lever; additional levers are a cap on materialized ships, budgeted materialization, and low-rate compact network sync.

### Cited Findings
- **Sable architecture:** sub-levels are "interactive physics moving block structures" holding normal chunks, entities and block entities at a separate dynamic pose; Rapier (Rust natives) is the default physics pipeline; Sable is "an incredibly intrusive mod" that "makes extensive use of mixins" and is "prone to extensive compatibility issues". — [Sable GitHub](https://github.com/cakeGit/sable)
- **Sable Optimizer (NeoForge 1.21.1, server-side):** inactive = velocity < 0.01 for 400 ticks (balanced). Presets: Quality/Balanced/Performance set inactive heatmap interval 40/10/70 ticks, active heatmap 4/4/8, inactive pose substep interval 5/5/8, inactive actor interval 4/4/8. It also skips ticks of idle Create kinetic block entities and collision/actor ticks of stationary contraptions, and sends kinetic sync every 4 ticks instead of every tick ("75%" fewer packets). No CPU/TPS benchmarks are given; the page says real gains need config edits. — [Sable Optimizer on CurseForge](https://www.curseforge.com/minecraft/mc-mods/aeronautics-sable-optimizer)
- **World Engine addon:** claims performance without lowering solver quality or collision precision (keeps Sable's substeps/timestep). — [World Engine on CurseForge](https://www.curseforge.com/minecraft/mc-mods/world-engine) (search snippet; benchmark page not readable)
- **Sable: Destructive (1.21.1 NeoForge):** server-side effect and destruction budgets, spatial/temporal deduplication, "Deferred Sable mutations at safe tick boundaries", heavy impacts sent as "one compact event packet" with visuals built client-side. — [Sable: Destructive on Modrinth](https://modrinth.com/mod/sable-destructive)
- **C2ME needed a "bandaid for create aeronautics"** (0.4.0.112), Create Aeronautics being Sable-based. — [Modrinth API: C2ME NeoForge 1.21.1](https://api.modrinth.com/v2/project/c2me-neoforge/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **Valkyrien Skies (anecdotal):** a 1.20.1 Forge server owner reported TPS falling from 20 to 10–5 over an hour with VS + Clockwork, staying at 20 after removing them. — [Answer Overflow thread](https://www.answeroverflow.com/m/1429172741222961253). A fix mod for the VS Space War addon says each projectile sent a sync packet to every player every physics tick. — [VSSW Performance Fix](https://www.modpackindex.com/mod/102332/vssw-performance-fix)

### Inferences
- Keep the existing rule (time-based simulation far away, Sable only near players) and add a hard cap on concurrently materialized Sable ships per player area, with priority by distance and battle relevance.
- Materializing a ship is a bulk block copy into a sub-level, so it belongs in the same budgeted placement queue as cities (spread over several ticks), and de-materialization should happen with hysteresis (materialize at R, de-materialize at R + margin) to avoid thrashing at the edge.
- For ships at sea that are materialized but idle (moored, becalmed), letting them come to rest lets Sable Optimizer-style inactivity rules apply; the mod's own sea swell forces on hulls may keep them "active" forever, which is worth checking against Sable Optimizer's velocity threshold.
- Far-ship positions for the map/sprites should go over the mod's own payload at low rate (e.g. 1–2 Hz, interpolated client-side), never per physics tick per player (the VSSW lesson).

### Gaps
- Sable's own threading (whether Rapier steps on the server thread or a native thread), sleeping support, and recommended ship counts are not documented in reachable sources; the Sable developer wiki was not fetched.
- No benchmarks for Sable or Valkyrien Skies server cost per ship were found.

## Data and network (SavedData cost, splitting, Codec vs NBT, payload limits, targeted sending, rate limiting)

### Takeaway
On NeoForge 21.1 the SavedData file write is already off-thread; the main-thread cost is building the `CompoundTag` and NeoForge's full `copy()` of it, for every dirty SavedData, on every autosave. Split big state into several SavedData objects so only changed parts are serialized. Clientbound payloads are capped at 1 MiB (serverbound 32767 bytes), and NeoForge 21.1 transparently splits oversized packets for NeoForge clients, but sending less (deltas, targeted distributors) is still the real fix.

### Cited Findings
- **NeoForge 21.1 SavedData save path:** `SavedData.save(File, Provider)` returns immediately unless `isDirty()`; otherwise it calls the mod's `save(CompoundTag, Provider)` on the calling (server) thread, wraps it with the data version, makes a full `compoundtag.copy()` ("to handle mods that just append an existing Tag"), then queues `IOUtilities.writeNbtCompressed(copied, path)` via `IOUtilities.withIOWorker`, which chains `saveDataTasks.thenRunAsync(task, Util.ioPool())`; finally `setDirty(false)`. `DimensionDataStorage.save()` iterates every cached SavedData. — [MC/Neo 21.1.265 src: SavedData, IOUtilities, DimensionDataStorage](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Paper's equivalent:** serialization on the main thread, compression and write on a per-storage single-thread executor; synchronous on close. — [Paper patch "Write SavedData IO async"](https://ayakael.net/mirrors/papermc/src/commit/ca07564e47a84a1b934b4e14e5645c6c23d817d6/patches/server/Write-SavedData-IO-async.patch)
- **Save spikes in practice:** a Mojira report on 1.21.4 traces a periodic 3 s (later around 500 ms) spike to save methods. — [MC-279194](https://mojira.dev/MC-279194)
- **Payload size limits (1.21.1):** `ClientboundCustomPayloadPacket.MAX_PAYLOAD_SIZE = 1048576` and `ServerboundCustomPayloadPacket.MAX_PAYLOAD_SIZE = 32767`; `CompressionDecoder.MAXIMUM_COMPRESSED_LENGTH = 2097152`, `MAXIMUM_UNCOMPRESSED_LENGTH = 8388608`. — [MC/Neo 21.1.265 src](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar); docs state "Server-to-client payloads are capped at 1 MiB" and client-to-server must be under 32 KiB. — [NeoForge docs 1.21.1: payloads](https://docs.neoforged.net/docs/1.21.1/networking/payload)
- **NeoForge 21.1 automatic packet splitting:** `GenericPacketSplitter` (a Netty `MessageToMessageEncoder`, handler name `neoforge:splitter`) re-encodes each outgoing packet, and if it exceeds the limit (uncompressed 8 MiB when a compressor is present, else 2 MiB) slices it into `SplitPacketPayload` parts (up to 65535 parts), reassembled on the other side. It is registered as an `optional()` `commonBidirectional` payload and only active when `isRemoteCompatible(connection)` (the remote is NeoForge). `SplitPacketPayload` is `@Internal`. — [MC/Neo 21.1.265 src: GenericPacketSplitter](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar); [SplitPacketPayload javadoc (1.20.4)](https://mcstreetguy.github.io/NeoForgeJavaDocs/1.20.4-20.4.237/net/neoforged/neoforge/network/payload/SplitPacketPayload.html)
- **Third-party limit raisers exist** ("Payload may not be larger than 1048576 bytes" errors; Packet Fixer has 1.21–1.21.3 builds). — [Packet Fixer on Modrinth](https://modrinth.com/project/c7m1mi73/version/GeO0XKnh)
- **Targeted sending in 21.1:** `PacketDistributor` has `sendToPlayer`, `sendToPlayersInDimension`, `sendToPlayersNear(level, excluded, x, y, z, radius, payload...)` (via `PlayerList.broadcast`), `sendToAllPlayers`, `sendToPlayersTrackingEntity`, `sendToPlayersTrackingEntityAndSelf`, `sendToPlayersTrackingChunk(level, chunkPos, payload...)`; all accept extra payloads as varargs (bundled into one packet). — [MC/Neo 21.1.265 src: PacketDistributor](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Rate-limited sync examples:** Sable Optimizer sends Create kinetic sync every 4 ticks instead of every tick (75% fewer packets). — [Sable Optimizer](https://www.curseforge.com/minecraft/mc-mods/aeronautics-sable-optimizer). Sable: Destructive sends one compact event packet and lets clients build effects. — [Sable: Destructive](https://modrinth.com/mod/sable-destructive). The VSSW fix exists because a per-physics-tick packet went to every player. — [VSSW Performance Fix](https://www.modpackindex.com/mod/102332/vssw-performance-fix)

### Inferences
- **Split SavedData by change rate:** e.g. one SavedData for world map/geography (rarely changes), one per nation or per region for holds/characters (changes daily), one for battle/feud state (changes often). Only dirty ones are serialized and copied. Call `setDirty()` only when something actually changed, not every tick.
- **Cheap serialization:** pack bulk data into `putIntArray`/`putLongArray`/`putByteArray` (one tag per array) instead of one `CompoundTag` per entry; this shrinks both the main-thread build and NeoForge's deep `copy()`. Codecs are convenient but allocate intermediate `DataResult`/map objects per field, so hot or very large structures are usually hand-written (no benchmark found; see Gaps).
- **Map sync:** version each map region/tile; clients report or the server tracks the last version each player has; send only changed tiles, compressed (e.g. palette + RLE or `Deflater` on byte arrays) and only to players who opened the map or are in that dimension. Keep each payload well under 1 MiB even though NeoForge would split it: splitting costs an extra full encode plus array copies on the Netty thread and fails for non-NeoForge clients.
- **Battle/ship state:** use `sendToPlayersNear` or `sendToPlayersTrackingChunk` with low frequency and client interpolation rather than `sendToAllPlayers`.

### Gaps
- No benchmark comparing Codec vs manual NBT encode cost on 1.21.1 was found.
- The default autosave interval and whether NeoForge 21.1 exposes a per-SavedData async hook beyond `IOUtilities` were not checked.

## Java-level techniques (fastutil, avoiding boxing/streams, MutableBlockPos, packed longs, spatial hashing, caches, reflection, event-bus overhead)

### Takeaway
fastutil ships with Minecraft and is what vanilla uses for hot maps; Lithium's gains come largely from cutting allocations and indirection in hot loops. On NeoForge, the main event-bus cost is the number of per-entity-per-tick events (`EntityTickEvent` fires for every entity and its `Pre` is cancellable), so a mod with its own unit list should tick once per server tick instead of listening to per-entity events.

### Cited Findings
- **fastutil is already on the classpath:** `ChunkMap` imports `Int2ObjectOpenHashMap`, `Long2ByteOpenHashMap`, `Long2LongMap`, etc. — [MC/Neo 21.1.265 src: ChunkMap](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Lithium's allocation and collection work:** `mixin.alloc` ("Patches that reduce memory allocations": `entity_iteration`, `entity_tracker`, `deep_passengers`, `chunk_random`) and `mixin.collections` (`entity_by_type`, `brain`, `entity_ticking`, `mob_spawning`). — [Lithium NeoForge mixin config](https://raw.githubusercontent.com/CaffeineMC/lithium/develop/lithium-neoforge-mixin-config.md)
- **NeoForge event bus on 21.1:** the project resolves `net.neoforged:bus` 8.0.5 (Gradle cache). `EntityTickEvent.Pre` implements `ICancellableEvent`; `EntityTickEvent.Post` does not. — [Gradle cache: net.neoforged/bus/8.0.5](file:///C:/Users/carat/.gradle/caches/modules-2/files-2.1/net.neoforged/bus/8.0.5); [MC/Neo 21.1.265 src: EntityTickEvent](file:///C:/Users/carat/Downloads/AI%20Modding/RafasConquest/build/moddev/artifacts/neoforge-21.1.265-sources.jar)
- **Event dispatch cost data (Forge's bus, not NeoForge's):** MinecraftForge EventBus PR #85 moves per-listener checks to registration time for events that are final, not `@Cancelable` and not generic; its benchmark reports about 961 ns/op posting to 100 static listeners. Cancellable events do not get this fast path. — [MinecraftForge/EventBus PR #85](https://github.com/MinecraftForge/EventBus/pull/85). NeoForge docs note priorities are ignored for events fired in parallel. — [NeoForge docs 1.21.1: events](https://docs.neoforged.net/docs/1.21.1/concepts/events)
- **FastEvent mod** (abandoned) claimed 6.4% faster registration and 24% faster repeated posting; its author notes NeoForge does not let mods modify the EventBus. — [FastEvent on Modrinth](https://modrinth.com/mod/fastevent)

### Inferences
- **Event listeners:** a listener on `EntityTickEvent.Pre/Post` runs once per entity per tick for every entity on the server (thousands), so the first line must be a cheap `instanceof`/flag check, or better, avoid it: keep the mod's own `Int2ObjectOpenHashMap<UnitState>` of battle units and process them in `ServerTickEvent.Post`. Same for `LivingIncomingDamageEvent`/`LivingDeathEvent`: filter early.
- **Hot-loop rules:** no streams/lambdas/`Optional` in per-unit-per-tick loops; `BlockPos.MutableBlockPos` reused per loop; positions as `long` via `BlockPos.asLong`/`ChunkPos.toLong` in `Long2ObjectOpenHashMap`/`LongOpenHashSet`; `IntArrayList`/`ObjectArrayList` instead of `ArrayList<Integer>`; squared distances instead of `Math.sqrt`.
- **Spatial hashing:** one grid per battle or per hold (cell = 8 or 16 blocks, key = packed cell long), rebuilt or incrementally updated as units move; neighbour and nearest-enemy queries read 9 cells instead of walking entity sections via AABB queries.
- **Caches with invalidation:** cache derived values (army strength per nation, route costs, hold lookups by chunk) with a version counter bumped on change instead of recomputing per tick; Lithium's `memory_changes` idea (skip work when inputs did not change) is the model.
- **Reflection:** replace hot-path reflection into Recruits/Sable/vanilla with access transformers (vanilla) or one-time `MethodHandle`/`VarHandle` lookups stored in `static final` fields; better still, call public API.

### Gaps
- No benchmark of NeoForge bus 8.x dispatch cost was found; the Forge PR numbers are for a different codebase.
- No source measured the gain from replacing AABB entity queries with a custom spatial grid in a Minecraft mod.

## Lessons from Lithium, FerriteCore, ModernFix, C2ME, Moonrise, ServerCore and Paper patches, and compatibility rules for a content mod

### Takeaway
The performance mods share three rules a content mod can follow: never change vanilla behaviour, make each optimization independently switchable, and never assume ownership of vanilla internals (chunk system, state maps, shapes). The biggest compatibility risks for RafasConquest are its mixins on `ChunkMap`/`TrackedEntity` (Moonrise replaces the chunk system; C2ME rewrites scheduling) and any world access from non-main threads or worldgen threads (C2ME sanitizers).

### Cited Findings
- **Lithium:** aims to optimize "without changing game mechanics or visuals" and without compromising compatibility; optimizations are largely independent and can be disabled one by one to resolve conflicts; options with unresolved major issues are disabled by default; NeoForge-specific `mixin.chunk_load_tricks` exists for "NeoForge's chunk loading tricks" and must stay enabled. — [Lithium GitHub](https://github.com/CaffeineMC/lithium); [Lithium NeoForge mixin config](https://raw.githubusercontent.com/CaffeineMC/lithium/develop/lithium-neoforge-mixin-config.md). Lithium has had native NeoForge 1.21.1 builds since Oct 2024. — [Modrinth API](https://api.modrinth.com/v2/project/lithium/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **FerriteCore:** replaces each BlockState's neighbour `Table` with a per-block `FastMap` (about 600 MB saved in its test), replaces the per-state property `ImmutableMap` with a FastMap-backed map (about 170 MB), deduplicates block-state shape caches by swapping VoxelShape internals (relies on shapes being immutable after creation), deduplicates baked quad vertex arrays ("not technically 100% safe" if arrays are modified), and keeps only entity/block-entity sub-tags of partially loaded chunk NBT on the server (90–100 MB). — [FerriteCore summary.md](https://github.com/malte0811/FerriteCore/blob/main/summary.md)
- **Moonrise:** most of its changes are in Paper; replaces the chunk system wholesale and auto-disables conflicting parts of Lithium and FerriteCore; incompatible with C2ME and ScalableLux. — [Moonrise GitHub](https://github.com/Tuinity/Moonrise)
- **C2ME:** UWRAD world-random sanitizer; worldgen-thread checks (scheduled tick access, item drops); compat fixes for Create, Twilight Forest, ServerCore, Create Aeronautics in its 1.21.1 changelog. — [C2ME GitHub](https://github.com/RelativityMC/C2ME-fabric); [Modrinth API: C2ME NeoForge 1.21.1](https://api.modrinth.com/v2/project/c2me-neoforge/version?loaders=%5B%22neoforge%22%5D&game_versions=%5B%221.21.1%22%5D)
- **ServerCore:** behaviour-changing features off by default; EAR, dynamic distances/mobcaps, villager lobotomization; NeoForge 1.21.1 builds. — [ServerCore GitHub](https://github.com/Wesley1808/ServerCore)
- **Paper patches applicable as patterns:** no chunk loads during pathfinding (`getBlockStateIfLoaded` → `BLOCKED`) — [patch](https://ayakael.net/mirrors/papermc/src/commit/38e1465620f2a0e0baf2b6156df72f653be80781/patches/server/Do-not-load-chunks-for-Pathfinding.patch); async SavedData IO — [patch](https://ayakael.net/mirrors/papermc/src/commit/ca07564e47a84a1b934b4e14e5645c6c23d817d6/patches/server/Write-SavedData-IO-async.patch).
- **Sable itself is mixin-heavy and compat-prone.** — [Sable GitHub](https://github.com/cakeGit/sable)
- **ModernFix** appears in 1.21.1 results mainly for a concurrency fix in `ForgeRegistryTagManager`. — [ModernFix version on Modrinth](https://modrinth.com/mod/modernfix/version/N9LUsEeT)

### Inferences
- **Compat rules for RafasConquest's own code:**
  1. Do not mutate `VoxelShape`s or baked-quad vertex arrays after creation (FerriteCore dedups them).
  2. Do not depend on `StateHolder#getValues()` being an `ImmutableMap` or on vanilla's neighbour `Table` (FerriteCore).
  3. No `Level.random`, `getChunk`, `setBlock` or entity spawning from worker or worldgen threads (C2ME sanitizers); worldgen code uses only the `WorldGenLevel`/`WorldGenRegion` it is given and its own seeded `RandomSource`.
  4. Keep the `ChunkMap`/`TrackedEntity` battle-camera mixins minimal, prefer `@Inject`/MixinExtras wrappers over `@Overwrite`/`@Redirect`, mark them non-required where a fallback exists, and test with Moonrise and C2ME installed (Moonrise replaces the chunk system; its entity-tracker changes were not verified here). A NeoForge-API alternative for keeping entities tracked around a camera (for example a server-side camera entity or extra chunk tickets plus `sendToPlayersTrackingChunk`) would remove the risk entirely.
  5. Make each heavy feature (battle LOD, city placement budget, map sync rate) a config value, the way ServerCore and Sable Optimizer expose theirs, so servers can tune without code changes.
- On NeoForge 1.21.1, Canary/Radium (Forge-era Lithium ports) are unnecessary because Lithium ships native NeoForge 1.21.1 builds (inferred from the Modrinth version list above).
